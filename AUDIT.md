# Clipahoy Archive Audit

**Subject:** WildFilmsIndia YouTube archive (Wilderness Films India Ltd.)
**Question:** what can this archive actually support, as a product?
**Method:** measured from the data. Where a number could not be computed, it says so.

> **This document is a record of an investigation, not a status page.** Sections A
> and D have been corrected to the current data (73,415 clips, 58,393 located).
> Everywhere else, figures are as measured at the time of the finding and are
> left standing so the reasoning still reads — §L in particular quotes a
> 66,132-clip index because that is what it was proposed against. For what is
> true today, read **STATUS.md**.

**Headline:** the archive is large, real, and commercially interesting. It does **not**
support the personalised-hometown product as specified. Two of three kill criteria fail,
and they fail on structure rather than on tuning — no amount of further extraction work
closes them. Section K proposes what the archive does carry.

## A. Sources inventory

Every data source in the repository. There is **no** Wilderness Films internal catalogue,
licensing database, hand-curated tag spreadsheet, transcript/caption file, or thumbnail
dataset. Everything below is derived from the YouTube Data API. This was confirmed by a
filesystem sweep for `*.csv`, `*.db`, `*.sqlite*`, `*.parquet`, `*.xlsx`, `*.srt`, `*.vtt`,
`*.tsv` across the repo (excluding `node_modules`, `.next`).

| Path | Format | Rows | Schema | Role |
|---|---|---|---|---|
| `data/.ingest-cache.jsonl` | JSONL | 126,524 | YouTube `playlistItem`: `kind, etag, id, snippet{publishedAt, channelId, title, description, thumbnails, channelTitle, playlistId, position, resourceId{kind,videoId}, videoOwnerChannelTitle, videoOwnerChannelId}`, plus injected `playlistTitle` | **Source of truth.** Append-only, streamed on read. | `data/index.json` | JSON | 73,415 clips / 231 places | clips: `id, title, text, placeId (nullable), subjects[], year, isPlaceholder` · places: `id, name, district, state, country, region, terrain, lat, lng` | Derived. What the app reads. |
| `data/gazetteer.json` | JSON | 234 places, 66 aliases | `places{id:{name,district,state,country,region,terrain,lat,lng,kind}}`, `aliases{}` | Extraction lookup. Generated by `scripts/build-gazetteer.ts`. |
| `data/unmatched.json` | JSON | `noPlace` 29,298 · `noSubject` 26,257 · `rejected` 468 | `{id,title}` | Extraction diagnostics. |

**Relationship and conflicts.** `index.json` is a strict derivative of `.ingest-cache.jsonl`:
126,524 rows → 88,159 unique videos (deduped by `snippet.resourceId.videoId`) → 73,415
indexed, of which 58,393 carry an identified place. No source disagrees with another because no second source exists. This
is a single-source audit, and every downstream number inherits whatever biases YouTube
metadata carries.

**Coverage gap in the source itself.** The channel reports **126,008 videos**; the cache holds
**88,159 unique (70%)**. The missing 30% is not a crawl failure — YouTube hard-caps a channel's
*uploads* playlist at 20,000 items regardless of quota. The remaining reach came from crawling
1,249 individual playlists (uncapped), at ~2,100 units of the 10,000/day free tier. The final 30% is **not**
reachable by any method available here — see the correction below.

> reached by `search.list` date-windowing at ~312,000 units (≈31 days of free
> quota). **That is wrong, and the cost estimate describes a method that does not
> work at all.** Tested directly against the channel: `search.list` scoped to this

## B. Definitions

Used consistently throughout. Any later deviation is stated explicitly.

**Identified location.** A place name resolving to exactly one row in the 234-place
gazetteer, via the cascade in §C. Gazetteer rows carry `kind: 'city' | 'state'`. There are
no district-level or country-level rows, so those granularities report zero by construction,
not by absence of evidence.

**Usable clip.** A record with **(a)** an identified location at `kind: 'city'` (town/city
granularity or finer) **and (b)** at least one subject tag from the 15-tag controlled
vocabulary. State-level-only locations do not qualify — "somewhere in Rajasthan" cannot
anchor a place-based product.

**Duration is unmeasured, and the original ≥15s clause is dropped from this definition.**
YouTube's `playlistItems.snippet` does not carry duration; obtaining it requires a separate
`videos.list` call per 50 video IDs (~1,764 additional quota units for 88,159 videos). That
call was not made. Duration is therefore unknown for 100% of the corpus and is treated as an
enrichment candidate in §J, not as a filter here.

**Reliable date.** A filming date from an explicit metadata field. **This field does not
exist in any source.** See §F. Year values in `index.json` are *inferred from text* and are
labelled as such everywhere they appear.

**A note on overlapping counters.** `noSubject` (26,257) and `noPlace` (29,298) are **overlays on matched clips**,
not a disjoint rejection bucket — those clips have a place but no subject tag and are
deliberately retained in the index (untagged clips remain findable via prose search). The
ingest script prints matched / noPlace / noSubject / rejected as a stacked list, which reads
as if they partition the corpus. They do not — a clip with a subject but no place is counted
in both `matched` and `noPlace`. Only `rejected`, and clips with neither signal, are actually
excluded. The ingest output now labels these lines `(overlaps matched)`.

## C. Location extraction methodology

### Source
**A hand-built 234-place gazetteer** (`data/gazetteer.json`), not GeoNames or any external
authority. 32 Indian states/UTs, 157 Indian cities/towns, 45 places outside India, 66 aliases. Coordinates are settlement centroids
(~1km accuracy); they are stored but unused by retrieval, which matches on name/district/state
strings. No external gazetteer was pulled.

This matters for reading §D: **"no identifiable location" conflates extraction failure with
gazetteer coverage gaps.** A real Indian town absent from a 234-entry list registers as
"no location" even when extraction correctly saw a proper noun. §E-0 (Step 0) disentangles
the two.

### Normalization
Lowercase; strip non-alphanumeric except apostrophes; whole-word boundary matching so "Goa"
does not fire inside "Goalpara". No diacritic folding (the corpus is overwhelmingly ASCII
transliteration).

### Historical and colonial names
Handled via the alias table: Bombay→Mumbai, Calcutta→Kolkata, Madras→Chennai,
Bangalore→Bengaluru, Poona→Pune, Mysore→Mysuru, Cochin→Kochi, Trivandrum→Thiruvananthapuram,
Benares/Banaras/Kashi→Varanasi, Gurgaon→Gurugram, Pondicherry→Puducherry, Orissa→Odisha,
Prayagraj→Allahabad, Alleppey→Alappuzha, Mangalore→Mangaluru, Cherrapunji→Sohra,
Baroda→Vadodara, plus 13 Delhi landmarks (Jama Masjid, Connaught Place, Sarojini Nagar,
Hauz Khas, Red Fort, Qutub Minar, …) and Taj Mahal→Agra.

### Fields searched — the cascade
Four zones, in strict priority order. This **is** the shipped method; it is audited as one
pipeline, with per-zone precision reported so the aggregate is not a black box.

1. **Playlist title** — channel-curated grouping ("Gurudwara, Delhi"). Highest trust: a human
   wrote it to group footage.
2. **Hashtag block** — pre-normalised tokens (`#khichan #rajasthan`).
3. **Video title**.
4. **Prose** — the written paragraph of the description, **truncated to its first two
   sentences** (see below).

Within a tier, a `kind:'city'` match outranks a `kind:'state'` match (prefer specificity).
The SEO keyword tail of descriptions is **never** consulted — it name-drops states for reach,
not because footage was shot there.

### The prose truncation, and why
The first audit of the full cascade scored **78.0%**, below the 80% bar, and the cause was
localised: prose scored **57.1%** while title (94.3%), hashtag (88.9%) and playlist (81.0%)
all cleared it. The failure was not noise but *drift* — descriptions open by stating what the
clip shows, then wander into background: a river's course through other states, where an
interviewee took their degree, which region a dance form originates from. All read as
locations; none is where the camera was.

Two structural fixes were tested against the same 100 records:

| | (a) prose confirms only | (b) prose = first 2 sentences |
|---|---|---|
| Precision | 81.7% | **88.0%** |
| Errors fixed | 13 of 22 | 13 of 22 |
| Records losing their location | 23 | **9** |

Option (a) was rejected on measurement: **16 of the 20 correct prose matches had no
corroborating signal from any other zone**, so forbidding prose from originating a location
discards most of what it legitimately contributes. Option (b) was applied
(`PROSE_SENTENCE_LIMIT = 2` in `scripts/lib/extract.ts`).

### Confidence threshold
Binary. A gazetteer/alias hit at a word boundary in a consulted zone is "identified"; anything
else is not. There is no probabilistic score, so no tunable threshold — a deliberate
simplification, and a limitation.

### Precision — 100-record hand audit (seed 42, mulberry32)

Sampled **from the post-fix index**, meaning these are *different* records than the 100 used
to select the fix. Scoring the tuned sample would have been overfitting; this is a fresh
measurement.

| Zone | Precision | n |
|---|---|---|
| Prose (truncated) | **95.7%** | 23 |
| Playlist title | 91.7% | 24 |
| Title | 91.1% | 45 |
| Hashtag | 87.5% | 8 |
| **Overall** | **92.0%** | 100 |

Prose moved 57.1% → 95.7%. Full judgments in `data/audit/step3-hand-audit-v2.csv`.

**Recall cost:** match rate fell 67.4% → 61.0% (59,388 → 53,821 clips). Prose-sourced
locations halved, 22,822 → 13,973. This is a deliberate trade: a smaller corpus we can trust
over a larger one we cannot.

### Known limitations — not fixed, not hidden

**1. Same-name collisions.** Neither fix touches these, and both remaining examples survived
into the final extractor:
- **Puri** (Odisha) matched the actor **Om Puri**'s surname.
- **Srinagar** (J&K) matched a clip about **Srinagar, Garhwal** — a different town of the same
  name in Uttarakhand.
The gazetteer has no disambiguation mechanism: no place-type corroboration, no co-occurrence
check against expected district/state, no person-name exclusion at match time. This is a real,
open defect.

**2. Origin-vs-filming-location.** The largest remaining error class in the final audit
(4 of 8 errors). A Republic Day tableau *from* Tripura filmed *at* the Delhi parade extracts
Tripura; a Kolkata dance group performing *in* Delhi extracts Kolkata. The metadata frequently
states provenance and venue in the same sentence, and the extractor cannot tell them apart.

**3. Descriptor-as-location.** "Kerala long lappet goat" (a breed) extracts Kerala; "Bengali
bride" (an ethnicity) extracts West Bengal. Filming location unknown in both.

**4. Subject-matter interviews.** An interview *about* Ayodhya is not footage *of* Ayodhya.
Correctly caught in some cases, missed in others.

## E. Metadata shape observations

Qualitative, 100 records, **seed 43** (disjoint from the location audit).
Records in `data/audit/step5-sample.json`.

**Descriptions are unusually rich and highly templated.**
- Length: min 791, median **2,011**, max 4,780 characters. **Zero empty descriptions in 100.**
- Three-zone structure, consistent across the corpus: prose paragraph → hashtag block →
  SEO keyword tail.
- 27/100 carry a hashtag block; 84/100 carry a playlist title.

**Titles are descriptive, not templated stock-footage codes.** Written for humans:
> "Dense forest canopy in Uttarakhand | Lush green woodland landscape"
> "Woman harvests mustard crop on terrace farms in rural India"
> "Black-headed Jay Perched on a Leafless Tree | Jabberkhet Mussoorie Wildlife"

- 0/100 ALL-CAPS; 18/100 use a colon; 7/100 use a pipe delimiter. Encoding is clean.
- 0/100 non-Latin script in this sample, though Devanagari titles do exist in the wider corpus.

**Locations appear inconsistently and at mixed granularity** — sometimes city, sometimes state,
sometimes a named institution, sometimes only in the description, sometimes only in the
playlist name. There is no dedicated location field anywhere.

**Recurring problems:**
- Boilerplate dominates: "This footage is part of the broadcast stock footage archive of
  Wilderness Films India Ltd…" appears in a large share of descriptions and is pure noise.
- One typo is systematic: **"Jabberkhet" vs "Jabbarkhet"** in the same corpus.
- Archival material is flagged in prose only — "circa 1989", "1980's archive", "old footage" —
  never in a field.
- One sample record retains a raw production code: `"SG 406 The Man talks about … MPCL DISC 2 FOOTAGE"`.

## F. Temporal coverage

| Category | Count | % |
|---|---|---|
| **Confirmed filming date (explicit field)** | **0** | **0.0%** |
| Inferred filming period (year token in title/prose) | 15,470 | 28.7% of matched |
| Upload date only | 38,351 | 71.3% of matched |

**There is no filming-date field in any source.** YouTube's `playlistItems.snippet` provides
`publishedAt` — upload date — and nothing else. `index.json`'s `year` is extracted from year
tokens appearing in title or prose text and is **inferred, not confirmed**. Upload date is
never used as a date proxy: this archive publishes digitised 1980s celluloid in the 2010s, so
upload date would be actively wrong.

Inferred-year distribution by decade (**not** confirmed filming dates):

| Decade | Clips | | Decade | Clips |
|---|---|---|---|---|
| 1930s | 548 | | 1980s | 851 |
| 1940s | 509 | | 1990s | 1,609 |
| 1950s | 827 | | 2000s | 2,699 |
| 1960s | 533 | | 2010s | 5,753 |

## G. Licensing / searchability

Eight queries run against title + prose of the current index. Top-10 relevance judged by hand.

| Query | Candidates | Top-10 precision | Failure mode |
|---|---|---|---|
| Kerala backwaters | 202 | **10/10** | — |
| Himalayan landscape | 7,401 | **10/10** | Recall far too broad to be useful as a filter |
| Kolkata tram | 48 | 5/10 | Fills with non-tram Kolkata footage (Howrah Bridge, colleges) |
| Indian wedding | 508 | 4/10 | Flower-market footage dominates; "wedding" matches supplier context |
| Indian street market | 4/10 | 4/10 | Drifts to food-production clips |
| Delhi railway station | 800 | 3/10 | "Delhi" is so dominant that any Delhi clip ranks |
| Mumbai monsoon | 146 | ~2/10 | Bollywood interviews mentioning Mumbai; one result in Gujarat |
| Rajasthan village | 536 | ~1/10 | Returns Demoiselle crane footage; "village" is not a subject tag |

**Average top-10 precision ≈ 48%.**

> **⚠️ SUPERSEDED.** This was measured before BM25 ranking existed — §G's own
> diagnosis was that results came back in index order with no ranking at all.
> The search layer now scores **97.0% precision@20** over a fixed 25-query
> benchmark that includes these eight queries; see `scripts/benchmark-queries.json`
> and STATUS.md. The 48% figure is kept because the kill-criteria reasoning in
> §I rests on it, and rewriting it would misrepresent what was decided and why.

**Verdict.** A filmmaker could find footage for *some* queries — anything matching the
controlled subject vocabulary and a well-covered place works well (Kerala backwaters is
flawless). But the archive is not reliably searchable with current metadata. Three specific
failures block professional use: there is **no relevance ranking** (results are index order,
so "Delhi railway station" returns whichever Delhi clips come first among 800), the **15-tag
vocabulary does not cover common licensing concepts** ("village", "tram", "wedding" are not
tags, so those queries degrade to substring matching), and **place dominance swamps subject
intent** — a query naming a big city returns that city, largely ignoring the rest of the
query. A researcher would find the Kerala backwater material immediately and would probably
conclude, wrongly, that the archive has little tram footage.

## H. Data problems observed

1. **30% of the channel is unreachable** without a quota increase (YouTube's 20,000-item
   uploads cap; playlists recovered to 70%).
2. **No filming-date field**, corpus-wide (§F).
3. **No duration field** without a further ~1,764 quota units (§B).
4. **Same-name collisions unresolved** — Puri/Om Puri, Srinagar J&K/Srinagar Garhwal (§C).
5. **Origin-vs-venue confusion** — largest remaining extraction error class (§C).
6. **Subject vocabulary too small.** 19,615 matched clips (36%) carry **zero** subject tags;
   the 15-tag vocabulary cannot describe a general factual archive containing tribal dance,
   industrial processes, political rallies, and 4,493 wildlife clips.
7. **Severe place concentration.** Delhi alone dominates; the top 6 places hold ~37% of the
   index. 100 of 150 usable places are effectively long-tail.
8. **A large non-archive content cluster** — 35.2% of unmatched is Bollywood/celebrity/format
   content that arguably should not be in a factual archive product at all.
9. **The archive is not India-only** (§E-0) — a scope decision, not a defect.
10. **Boilerplate and one systematic typo** (Jabberkhet/Jabbarkhet) in descriptions (§E).
11. **Misleading ingest output** — matched/noPlace/noSubject/rejected print as a stacked list
    but noSubject is a subset of matched, not disjoint (§B).

## I. Kill criterion evaluation

Applied mechanically. Thresholds fixed before the numbers were known.

| # | Criterion | Threshold | Measured | Result |
|---|---|---|---|---|
| 1 | Places with 20+ usable clips | ≥ 200 | **115** | ❌ **FAIL** |
| 2 | Corpus with city/town-level location | ≥ 40% | **30.0%** | ❌ **FAIL** |
| 3 | Precision, manual location audit | ≥ 80% | **92.0%** | ✅ **PASS** |

**Two of three fail.**

Criterion 1 fails at 58% of target. Criterion 2 fails at 75% of target. Neither is a near
miss that further extraction tuning closes:

- **Criterion 1 is capped by the gazetteer's real ceiling.** The playlist-title expansion —
  the highest-quality source available — added 34 places and recovered 3.4% of the unmatched
  pool. Reaching 200 places at 20+ usable clips each requires roughly 85 more well-covered
  places, and Step 0 measured the remaining genuine gazetteer gap at only ~3–4% of unmatched,
  concentrated on a small number of repeated names.
- **Criterion 2 is capped by what the metadata says.** 31.1% of the corpus resolves only to
  state level, because the source text itself says "in Uttarakhand" and nothing more precise.
  No extractor recovers a town that was never written down.

> **Recommendation: do not build the personalised-hometown product.** The autocomplete-of-covered-
> places approach starves at 115 viable places — most Indian users would type a hometown the
> archive cannot answer for, and the honest "we don't have this yet" state would be the modal
> experience rather than the edge case. Combined with §F (no reliable dates), the specific
> promise "film of your hometown, from your childhood" is not supported on either axis.

Note that **criterion 3 passes comfortably**. Extraction quality is not the problem. The
archive's *shape* is.

## J. Enrichment analysis

Five questions per candidate. Cost assumes ~$0.001/record for an LLM pass over 88,159 records.

### 1. Location normalization (more gazetteer places)
1. **Problem:** places absent from the 187-entry gazetteer register as "no location".
2. **Scale:** ~3–4% of the 33,818 unmatched pool ≈ **1,000–1,350 records**, concentrated on a
   small number of repeated names.
3. **Product-critical?** No. Already hit diminishing returns — the best available source
   (playlist titles) yielded 3.4%.
4. **Deterministic?** **Yes**, entirely. Gazetteer rows + aliases.
5. **Cost:** ~4–6 hours manual. **$0.** → **Do it. Cheap, but do not expect it to change §I.**

### 2. Subject tag extraction (expand vocabulary)
1. **Problem:** 15 tags cannot describe this archive; queries like "village", "tram",
   "wedding" have no tag to match.
2. **Scale:** **19,615 matched clips (36%) carry zero tags.**
3. **Product-critical?** **Yes** — for any subject-first or licensing-search product, this is
   the binding constraint (§G).
4. **Deterministic?** Partly. Expanding to ~50–60 tags with keyword rules covers most of it;
   the long tail is better served by full-text search, which already exists.
5. **Cost:** ~2 days engineering for a 50-tag vocabulary + re-extraction, **$0 in API**.
   LLM tagging of 88k records ≈ **$88 + ~1 day**. → **Do the rule-based expansion first.**
   The LLM pass has to beat free full-text search to justify itself, and against 2,000-character
   descriptions it may not.

### 3. Filming date inference
1. **Problem:** no reliable dates; blocks any era-based product.
2. **Scale:** **71.3%** of matched clips have no date signal at all.
3. **Product-critical?** Only for a nostalgia/era product — which §I already rules out.
4. **Deterministic?** Partially: regex already extracts explicit year tokens (28.7%). The
   remaining 71.3% mostly contains **no date information in any form** — an LLM cannot infer
   what isn't written.
5. **Cost:** LLM pass ≈ **$88**, with low expected yield and **no way to validate** the output
   against ground truth. → **Do not do this.** Fabricating dates for a memory product is the
   most damaging possible failure.

### 4. Historical name reconciliation
1. **Problem:** Bombay/Mumbai, Calcutta/Kolkata etc. fragment the same place.
2. **Scale:** already handled — 67 aliases; residual is small.
3. **Product-critical?** No. Largely solved.
4. **Deterministic?** **Yes.** Alias table.
5. **Cost:** ~1 hour per batch. **$0.** → **Maintain as encountered.**

### 5. Transcript extraction
1. **Problem:** spoken content is entirely unindexed.
2. **Scale:** **88,159 records — 100% have no transcript.**
3. **Product-critical?** No for browsing; potentially transformative for licensing search
   (dialogue, interview content, place names spoken but never written).
4. **Deterministic?** No. YouTube auto-captions can be fetched where they exist (coverage
   unknown, not measured); otherwise ASR.
5. **Cost:** caption fetch ≈ 1 unit/video ≈ **1,764 units** + engineering; third-party ASR at
   scale is **thousands of dollars**. → **Measure caption availability first (cheap), then decide.**
   Do not commit to ASR blind.

### 6. Thumbnail / frame scene classification
1. **Problem:** no visual index; metadata-only retrieval.
2. **Scale:** 88,159 records, thumbnails available free via `i.ytimg.com`.
3. **Product-critical?** No. Descriptions are unusually rich (median 2,011 chars) and already
   describe the visual content.
4. **Deterministic?** No — vision model required.
5. **Cost:** vision API over 88k thumbnails ≈ **$900–1,800** + several days. → **Do not do this
   now.** It duplicates information the descriptions already carry, at the highest cost of any
   option here.

**Summary:** do #1 and #4 (free), do #2 rule-based (the real constraint), measure #5 before
committing, and reject #3 and #6.

## K. Product directions

Grounded in what the audit measured, not in what was hoped for. §I rules out the
personalised-hometown product; none of these depend on it.

### Direction 1 — Subject-first archive browser *(recommended)*
- **User promise:** "See India's ordinary life on film, by subject — festivals, rivers, hill
  stations, railways."
- **Asked:** no personal questions. Pick a subject, optionally narrow by region.
- **Retrieval:** subject tag → place → prose full-text. Ranking by tag confidence then place depth.
- **Result:** a browsable reel per subject.
- **Hook:** recognition rather than autobiography — "this is exactly what a mela looks like."
- **Business:** consumer top-of-funnel feeding licensing enquiries.
- **Biggest risk:** 36% of matched clips are untagged (§J-2) — needs the vocabulary expansion first.
- **Evidence:** 10,446 festival / 8,181 river / 7,117 hills clips; 92.0% location precision;
  Kerala-backwaters query at 10/10.

### Direction 2 — Licensing search tool for filmmakers
- **User promise:** "Search four decades of Indian factual footage and request a licence."
- **Asked:** a free-text query.
- **Retrieval:** full-text over prose (median 2,011 chars/record) + place + subject facets,
  with **real relevance ranking** — the missing piece identified in §G.
- **Result:** ranked results with place, inferred period where known, licensing contact.
- **Hook:** none needed; this is a professional tool.
- **Business:** **direct revenue.** Wilderness Films already licenses; this is the shortest path
  to money and needs no consumer scale.
- **Biggest risk:** current top-10 precision averages 48% — ranking is the whole product.
- **Evidence:** §G; 66,132 indexed clips (57,688 located); 5,600+ with inferred pre-2000 dates.

### Direction 3 — Curated editorial around the strongest 30–50 places
- **User promise:** "The archive of Mussoorie / Varanasi / Kolkata, properly told."
- **Asked:** nothing; pick a place.
- **Retrieval:** hand-curated from the 58 places with 100+ usable clips.
- **Result:** an edited sequence with written context.
- **Hook:** depth over coverage — honest about being 50 places, not 5,000.
- **Business:** consumer/brand, SEO value for the sister-site network.
- **Biggest risk:** manual editorial cost; does not scale.
- **Evidence:** 58 places with 100+ usable clips; 6 with 500+.

**Scope decision still required (§E-0):** 14% of unmatched records are non-India footage —
Nepal, Bhutan, Tibet, Kenya, Thailand, Europe — at hundreds of clips each. Every direction
above needs an explicit call: expand scope, or filter to India-only. This is a positioning
question, not a data question, and it is not decided here.

## L. Recommendation and proposed prototype

**Recommendation: build Direction 2, the licensing search tool.**

It is the only direction whose value does not depend on the two things this audit found the
archive cannot do — anchor to a user's specific hometown (115 viable places, §I-1) and place
footage in a specific era (0% confirmed dates, §F). It is the only one with **direct revenue**
against an existing business line. And its single biggest weakness — 48% top-10 precision — is
a *ranking* problem, which is ordinary engineering, not a data-acquisition problem.

Direction 1 is the natural consumer follow-on once §J-2 (subject vocabulary) is done. Direction 3
is worth doing only if there is editorial appetite.

### Proposed prototype — the smallest thing that tests the real question

**"Does a researcher find something they didn't expect to exist?"**

A single search page over the existing 66,132-clip index. No accounts, no journeys, no sharing.

1. One search box, full-text over title + prose, **with BM25 relevance ranking** (the piece
   §G proved is missing).
2. Two facets only: place and decade-if-known — with the decade filter **labelled "inferred
   from description"** wherever it appears.
3. Results as thumbnail + title + place + honest date caption.
4. One button per result: "Request this footage."

**The test:** put it in front of 5–10 documentary researchers with real briefs. Measure only
two things — did they find something usable, and did they hit "Request"? Success is a request,
not a session length.

**Why this and not more:** it reuses the index as-is, needs no enrichment spend, no new API
quota, and no product decision on India-only scope. If researchers don't request footage from
66,132 clips with rich descriptions, no amount of tagging or transcription will save it — and
that is worth knowing before spending $88 on tags or thousands on ASR.

### PRNG

Node has no seedable RNG, so all sampling uses **mulberry32**, published here for
reproducibility in any language:

```js
function mulberry32(seed) {
  return function () {
    seed |= 0; seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}
// indices: draw Math.floor(rand() * poolSize) into a Set until it holds n, then sort ascending.
```
